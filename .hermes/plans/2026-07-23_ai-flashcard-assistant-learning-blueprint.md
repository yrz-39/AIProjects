# AI 问答卡与复习提纲助手：学习蓝图

> **For Hermes:** 以“用户主写、导师分关提示与审阅”的方式实施。每个功能先说明目标、动机、边界与所涉知识；用户先自行完成最小实现，再补测试、审阅边界并重构。

**Goal:** 用 Python 做一个本地运行的网页应用：用户录入一段课程笔记，保存到本地，并可请求大模型生成复习提纲或问答卡。

**Architecture:** 浏览器负责表单与结果展示；FastAPI 提供 HTTP 接口、验证输入并编排业务流程；SQLite 保存笔记和生成结果；独立的 LLM client 负责调用 OpenAI-compatible API。第一版只处理用户主动粘贴的一篇笔记，不扫描 Obsidian，不引入 RAG、向量数据库、Agent 或用户登录。

**Tech Stack:** Python 3.11、uv、FastAPI、Jinja2（可选，用于首屏 HTML）、原生 HTML/CSS/JavaScript、SQLite、pytest、OpenAI-compatible chat-completions API。

---

## 1. 产品边界

### MVP 要完成的闭环

```text
输入标题、课程、笔记正文
        ↓
本地保存笔记
        ↓
点击“生成”并选择模式（提纲 / 问答卡）
        ↓
后端将笔记与明确的 Prompt 发送给模型
        ↓
模型返回符合约定 JSON 格式的内容
        ↓
网页展示结果，并把结果关联保存到该笔记
```

### 第一版明确不做

- 自动读取整个 Obsidian vault；
- PDF/Word 文档解析；
- RAG、embedding、向量数据库；
- 多 Agent、长期记忆、自动任务；
- 用户注册、云端部署、多用户同步；
- 复杂 UI 与美术设计。

**验收标准：** 用户在本机浏览器中完成一次“保存笔记 → 生成 → 重启服务后仍能查看笔记和结果”。

## 2. 系统分层与数据流

```text
[Browser]
HTML 表单、按钮、结果卡片
        │ fetch + JSON
        ▼
[FastAPI routes]
HTTP 路由、请求/响应、状态码
        ▼
[Service layer]
输入校验、组装 Prompt、选择生成模式、处理错误
      ┌─┴──────────────┐
      ▼               ▼
[SQLite repository] [LLM client]
保存/查询数据        调用模型 API
      │               │
      └───────┬───────┘
              ▼
       返回结构化结果给浏览器
```

### 为什么要分层

- 路由不应直接写 SQL 或直接拼 API 请求；否则后续难测、难改。
- 数据库操作集中在 repository，未来换 ORM 或扩展表结构时影响较小。
- 模型调用集中在 client，便于替换模型、超时重试与模拟测试。
- service 是业务语义所在地：什么是“生成问答卡”、什么输入无效，都在这里讲清楚。

## 4. 数据模型（先小后大）

### `notes`：一篇原始笔记

| 字段 | 含义 |
|---|---|
| `id` | 自增主键 |
| `title` | 用户起的标题 |
| `course` | 如“数据结构”“ICS” |
| `content` | 笔记正文 |
| `created_at` | 创建时间 |

### `generations`：一次生成记录

| 字段 | 含义 |
|---|---|
| `id` | 自增主键 |
| `note_id` | 对应的笔记 ID |
| `mode` | `outline` 或 `flashcards` |
| `content_json` | 模型返回并验证后的 JSON 结果 |
| `created_at` | 生成时间 |

这里的关系是：**一篇笔记可以有多次生成记录**。这让将来修改 Prompt 或重新生成后，旧结果仍可回看。

## 5. API 设计（MVP）

| 方法与路径 | 用途 | 成功返回 |
|---|---|---|
| `GET /` | 返回网页 | HTML |
| `POST /api/notes` | 创建一篇笔记 | 新笔记 JSON，状态 `201` |
| `GET /api/notes` | 列出笔记摘要 | 笔记列表 JSON |
| `GET /api/notes/{id}` | 查看笔记与生成记录 | 完整笔记 JSON |
| `POST /api/notes/{id}/generations` | 请求生成提纲或问答卡 | 新生成结果 JSON |

### 要先写清的输入规则

- 标题只可为空时自动使用默认标题，或要求用户填入；二者选一种并测试。
- 课程字段可选。
- 正文不得为空；上限先设为一个可解释的字符数，避免误提交整本教材。
- `mode` 只接受 `outline` 与 `flashcards`。
- 不存在的 `note_id` 必须返回 `404`。
- 模型网络错误不能让服务崩溃，需返回可读错误信息。

## 6. AI 部分：真正要理解的内容

### 6.1 模型调用不是“魔法函数”

一次调用至少包含：

```text
模型标识
+ system message（角色、边界、输出规则）
+ user message（用户笔记）
+ temperature 等生成参数
+ API key 与 base URL
+ 超时、失败与返回内容解析
```

### 6.2 Prompt 的职责

Prompt 不是“写得越长越好”。它要明确：

1. 任务：生成提纲，还是问答卡；
2. 资料范围：只依据用户提供的笔记，不知道时说明；
3. 输出结构：字段名称、数组长度、文本语言；
4. 质量约束：避免无依据补充，问题应能由答案支持。

### 6.3 结构化输出

建议模型输出 JSON，而非一段自由文本。例如问答卡的概念模型：

```json
{
  "cards": [
    {"question": "什么是栈？", "answer": "……", "tag": "基础概念"}
  ]
}
```

学习重点不是死记 JSON，而是理解：**程序要继续处理模型结果时，机器可读的结构比漂亮的自然语言更可靠。**

### 6.4 必须接受的现实

- 模型会幻觉，不能把输出当教材标准答案；
- API 调用会失败、超时、限流；
- 笔记会被发送给所配置的模型服务，不能将个人隐私或敏感资料随意提交；
- `.env` 是密钥的本地容器，绝不提交到 Git。

## 7. 分阶段实现与对应知识点

### 阶段 A：项目与最小网页

**目标：** 浏览器能打开本地页面，提交一段文本后后端原样返回。

**学习点：**
- `uv` 与虚拟环境；
- `pyproject.toml`；
- HTTP 请求/响应、状态码、JSON；
- FastAPI 路由；
- 浏览器 `fetch()`；
- 前后端不等于两个神秘世界：它们只是用 HTTP 传数据。

**最小测试：** 空正文应被拒绝；普通正文应原样回显。

### 阶段 B：SQLite 笔记保存

**目标：** 创建、列出并查看笔记；服务重启后数据仍存在。

**学习点：**
- 表、行、主键；
- 参数化 SQL 与 SQL 注入边界；
- CRUD：Create / Read 是 MVP 首批需要的能力；
- Pydantic schema 与数据库行数据的差异；
- 为什么路由不应直接写 SQL。

**最小测试：** 创建后可查到；空内容不入库；不存在 ID 返回 `404`。

### 阶段 C：先用假 LLM 打通生成流程

**目标：** 在不使用真实 API 的前提下，让“生成问答卡”完整跑通。

**学习点：**
- 依赖注入的朴素思想：service 接受一个可替换的 client；
- 测试为什么不应每次都花钱调用真实模型；
- 输入、输出与异常契约。

**最小测试：** 假 client 返回固定卡片时，服务保存并返回该卡片。

### 阶段 D：接入真实模型 API

**目标：** 以 `.env` 中的配置调用 OpenAI-compatible API，生成提纲或问答卡。

**学习点：**
- 环境变量与密钥安全；
- HTTP 客户端、超时与异常；
- system/user message；
- Prompt 迭代；
- JSON 解析与不合法结果的防御。

**最小测试：** 模拟 API 返回不合法 JSON 时，系统给出受控错误，而非 500 崩溃。

### 阶段 E：结果页面与项目收束

**目标：** 页面可选择模式、显示加载状态、展示历史结果；陌生用户依 README 可在本机跑起来。

**学习点：**
- DOM 渲染、异步请求与加载状态；
- UX 中的错误提示；
- Git 提交粒度；
- README 是软件的一部分；
- 可复现运行比“我电脑上能跑”更重要。

**最小测试：** 完整 API 测试通过；手工验证从创建笔记到生成结果的一条路径。

## 8. 推荐推进节奏

不按日期强迫安排，只按“小闭环”推进：

```text
第 1 个闭环：文本提交 → 后端回显
第 2 个闭环：文本提交 → SQLite 保存 → 可查回
第 3 个闭环：请求生成 → 假 client 返回卡片 → 保存并展示
第 4 个闭环：真实 API 生成一份可用结果
第 5 个闭环：错误处理、测试、README
```

每次只推进一个闭环中的一小步：先明确当前功能的目标、输入输出与边界；用户自行写出最小实现；随后运行测试、补齐异常与边界用例，并在审阅后整理命名和结构。

## 9. 完成后你能带走什么

完成此项目并不等于“学会 AI”，但会得到一张很扎实的地图：

```text
Python 工程组织
+ Web 的请求/响应模型
+ 数据库持久化
+ 大模型 API 调用
+ Prompt 与结构化输出
+ 异常处理与密钥边界
+ 测试驱动的最小产品迭代
```

它也是下一项目“网易云学习音乐自动选择器”的共同地基：届时只需把 LLM 生成模块替换为“候选歌曲 → 特征打分 → 排序”，而 Web、SQLite、测试与项目组织都可以复用。
